## 2. ボトルネック分析（症状と原因を分ける）

### 症状

1. 到着率が約 150 req/s を超えると、応答時間が急増し（p95 数秒）、nginx の 504 が出る（`proxy_read_timeout 30s` に達した要求）。
2. その間、**health（`GET /api/v1/health`）の応答も 2〜4.7 秒に伸びる**。health は DB を開くだけの軽い処理なので、要求の種類に関係なく**待たされている**。
3. 高負荷の段のあとも、k6 の取りこぼし（dropped iterations）が出る（spike 全体で平均 9,500 件）。
4. 件数が増えると同じ到着率でも CPU 使用率が上がる（10,000 件では 20 req/s で CPU 71%）。

- **飽和資源は backend の CPU（1 vCPU の上限）**。100 req/s で CPU 77%、150 req/s 以上で 98〜102% に張り付く。frontend（nginx）の CPU は 5% 以下、負荷生成（k6）は 35% 以下で、**どちらも律速ではない**。メモリは 95 MiB（上限 512 MiB）で、増え続けてもいない。
- **待ち時間の正体は、Node の単一スレッドのイベントループの待ち**。CPU が 100% に張り付いた段で health が 2〜4.7 秒に伸びる。health 自体は軽いので、他の要求の処理が終わるまで順番を待っている（キューイング）。最終的に nginx が 30 秒で 504 を返す。
- **1 要求あたりの CPU 時間は約 6〜10 ms**（CPU% ÷ 到着率。20 req/s で 14%→7 ms、50 req/s で 31%→6 ms、100 req/s で 77%→8 ms）。1 vCPU が 100% になる到着率は 100 ÷ 6.5〜10 ms = 約 100〜150 req/s で、**観測した崩れ始め（150 req/s）と一致する**。

### 結論（症状と原因の対応）

- **原因**: backend が毎要求で「接続を開く → 全行を読んで検証 → 操作」を**同期（`node:sqlite` の DatabaseSync）**で行う設計。コストが件数に比例し、Node の単一スレッドで直列に処理される。CPU 上限（1 vCPU）で飽和し、飽和後は待ち行列がそのまま遅延と 504 になる。
- **症状**: 限界（約 100〜150 req/s、10,000 件では約 30 req/s）を超えると遅延・エラー。health まで遅れる。
- 想定利用（0.5 req/s）では 2 桁以上の余裕があり、現状で利用者に影響する問題は無い。**将来の件数増加と、複数クライアント・自動化・ブラウザの再試行が重なるときのための余裕を測った結果**として、以下の改善案を残す。

| --- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |

## 4. soak（時間劣化）

10 分（CI 短縮版）× 3 反復。20 req/s、追加と削除を同数にして件数を一定に保つ（balanced）。長時間版（2 時間以上）は**未実施**。

**結果（件数を一定にした run `results/soak-r2-*`）: pass。**

| 指標                                   | 実測（3 反復）                                                                                                 |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| list p95（全体）                       | 7.3 / 7.5 / 7.1 ms（SLO 500 ms）                                                                               |
| list p95 の前半 2 分 → 後半 2 分の変化 | +2.3% / +4.9% / +10.8%（判定: +20% 以内）                                                                      |
| エラー率                               | 0%                                                                                                             |
| backend メモリ（開始 → 終了）          | 40.7→44.1 / 41.2→41.4 / 41.9→42.4 MiB（増加比 1.08 / 1.01 / 1.01。+20% で警告、+50% で失敗の規則に対して余裕） |
| SQLite ファイル（開始 → 終了）         | 155,648 → 159,744 bytes（+4 KB。件数がほぼ一定）                                                               |

メモリ・DB サイズは増え続けておらず、**10 分の範囲では時間とともに悪化する傾向は見えない**。2 時間以上の長時間版・断片化の影響は未確認。

**最初の soak（main の run）が fail した経緯**（記録として残す）:

- main の run（`results/20261011T082949Z-f948648/soak`）は list p95 が前半 → 後半で +25.8% 悪化（> 20%）で **fail** だった（9.4 → 12.6 ms。メモリは平坦、DB は 155 KB → 450 KB に増加）。
- 1 回目の再実験（`results/soakfix-*`、削除対象が無いときの代替を修正）でも +37% で fail。DB サイズの増加（+168〜303 KB ≒ 1,000〜2,000 行）から、**件数が増えていた**と判断した。capacity の件数別 p95（約 +2.3 ms / 1,000 件）から見ても、観測した悪化（約 3 ms）と整合する。
- 原因は試験側の不備: 決定的な操作表（20 スロットを互いに素な歩幅で巡回）と VU の割り当て（VU 数が固定だと各 VU が見るスロットが 2 種類だけになる）の組み合わせで、追加ばかり受け持つ VU が生じ、削除が追い付かなかった。balanced ではプールを 2 件までに保つよう修正して再実験し、pass した。
- したがって「時間による劣化」ではなく「件数の増加による劣化」を、同じ規則（前半 → 後半の p95）が検出していた。規則の感度は期待どおりだった（件数が増えれば fail する）。main の run の soak 結果（fail）は削除せず、判定が試験の不備を拾った記録として残す。stress / spike も balanced を使うが、60〜180 秒と短く、件数の増加は小さい（影響は未評価）。

## 6. 試験で見つけた試験側の不備（記録）

### 8.3 反復の分散・判定の根拠・warm-up・外れ値

- **warm-up**: 各反復の最初に 30 秒（5 req/s）を別実行として流し、判定から除外した（`warmup.summary.json` は保存、判定に使わない）。screen は 3 回の読み込みを捨てた上で 10 回計測。反復ごとに DB ボリュームを作り直す。
- **判定の根拠**（`verdict_rule`、`verdict.json` に全文）: 統計量は p95（SLO にあるものは p99）。外れ値は上位 0.1%（n ≥ 100 のとき）を除いて p95 / p99 を求め、除外前の値は `raw_p95` などに併記。エラー率は `http_req_failed` と `checks` の大きいほう（< 1%）。SLO 違反は「3 反復の平均が目標を満たさない」で fail、反復の 1 つでも・95% 信頼区間の悪い側の端が満たさなければ warning。今回の load の warning は 0 件。
- **分散**（`variance_stats`、n = 3、t 分布）: load の list p95 は 19.364 / 19.534 / 19.603 ms（標準偏差 0.12 ms = 0.6%）、追加 p95 18.66 / 18.21 / 18.27、health p95 30.8 / 29.5 / 28.8 ms。backend の CPU 平均は 36.2 / 36.9 / 36.9%。**想定負荷の範囲では反復間のばらつきはとても小さい**。一方、**膝や飽和域では大きく揺れる**: stress の 100 req/s の list p95 は 162 / 174 / 205 ms（変動係数 約 12%）、load の p99 は 50 / 40 / 54 ms（約 15%）、spike の回復時間は 20 / 15 / 20 秒、capacity 7,500 件の list p95 は 5.14 / 6.07 / 5.15 秒。
- **共有ランナーのノイズについて、この 1 回の run で言えること**: 同じ run 内の 3 反復（約 6 分ずつ・直列）は、想定負荷で 1% 未満の差に収まった。**異なる run 間（別の日・別のホスト）の揺れは、この 1 回の実測では分からない**。同じ区分の baseline との比較（`compare.mjs`、+20% かつ絶対差の下限）で、次の run からばらつきを観測していく。隣のジョブの影響は観測できない（CPU 使用率は被試験の取り分に対する値で、ホスト全体の混雑は見えない）。

### 8.4 baseline と退行判定

- `perf/baseline.json` に runner の区分（`github-hosted:ubuntu24:X64`）の baseline `v1.0.0` を追加した（run 38152548008 の `metrics.json` の 27 指標。開発機の baseline `initial-main-6e5d2db` は残す）。
- `compare.mjs` は `env_class` が同じ baseline とだけ比べる。runner の run を `v1.0.0` と、開発機の run を `initial-main-6e5d2db` と比べると、それぞれの区分の基準が選ばれる（runner 27 指標・開発機 8 指標、いずれも退行 0 件）。baseline が無い区分は失敗にせず、作り方を出力する（run 38152548008 自体は baseline が無く「比較せず」だった）。
