## 2 優先度・実施必須区分

`priority` と `mandatory` は**別の軸**である。

### 2.1 優先度（priority）

high / medium / low。**ケースに紐づくリスクの priority の最大値**で決める（リスクの優先度は 02 の 2 章で 3 軸から導出）。優先度は、実施順序と、失敗したときの扱い（high の失敗はリリースを止める検討対象）を決める。

### 2.2 必須区分（mandatory）

| 値 | 意味 | 終了条件との結び付き |
|---|---|---|
| 必須 | 終了条件（リリース可否）に含める | **必須ケースがすべて合格**、または不合格が不具合として起票され重大度に応じた判断を受けていること。priority が high のケースはすべて必須 |
| 任意 | 終了条件に含めない。余力で実施し、結果は記録する | 不合格でもリリースを止めない（不具合は起票する）。暫定しきい値や暫定期待値のうち、確定していない部分を含むもの |
| 探索 | 手動の探索的確認。観察結果を記録して判断する | 実施の有無と観察結果を記録する。期待と異なる観察は不具合として起票する |

- 必須の決め方: (1) priority が high、(2) 仕様書の受け入れ条件（AC-01〜AC-07）または明示要求（§07）を直接確認するもの、のどちらかなら必須にする。リスクが low でも、仕様が明示する構成要求（compose 起動）は必須にする。
- 暫定期待値を含むケースでも、合否に含める部分が確定していれば必須のまま残し、未確定の部分は期待結果に「合否に含めない」と明記する。

## 3 前提条件

### 3.1 書き方

前提条件（`precondition`）は、**ユーザー・権限・データ状態・設定・環境**の 5 要素を、第三者が再現できるように書く。データ状態には、6 章のデータセット ID（DS-xxx）を使う。**他のケースの実施を前提にしない**（「TC-xxx の後」と書かない。必要な状態は、データセットの投入で作る）。

### 3.2 共通前提

| 区分 | 共通の内容 |
|---|---|
| ユーザー・権限 | ログインなし。認証・認可・権限の仕組みを持たない 1 人用で、全操作が許可される（仕様 §01）。API ケースは Authorization ヘッダ・Cookie を付けない |
| データ状態 | ケースごとにデータセット（DS-xxx）を専用の一時 DB へ投入する。DB はケースごとに新規作成する |
| 設定 | backend の DB パスとポートは、起動時の環境変数で指定する（ケースごとに別の値を使う）。compose ケースは専用のプロジェクト名と空きポート |
| 環境（e2e） | backend（Node.js 24 + Fastify）と frontend を起動し、frontend から `/api` を backend へ中継する。ブラウザは Chromium 最新安定版、画面幅 1280x800（360px のケースは 360x640）、新規ブラウザコンテキスト |
| 環境（api） | backend を起動し、HTTP クライアントから `/api/v1` を直接呼ぶ |
| 環境（unit） | Node.js 24（`mise.toml` で固定）の node:test。DB・ネットワーク・ブラウザを使わない |
| 環境（compose） | docker compose（テスト専用のプロジェクト名、専用ボリューム `todo-data`）で frontend と backend を起動する |

## 4 操作・入力の明確性

- **手順（`action`）は番号付きの複数行**（`1. …` `2. …`）で書き、1 行に 1 操作とする。操作の対象（行・ボタン・ヘッダ・ファイル）を名指しする。
- **入力（`input`）は具体値**で書く。長い文字列は生成式で示す（例: `"a".repeat(100)`、`"😀".repeat(100)`）。改行・空白は `\n`・`\r\n`・`"   "` のようにエスケープで示す。サロゲートペアや結合文字はコードポイント数と UTF-16 長を併記する。
- 「適当な値」「いくつか」のような解釈の余地のある表現を使わない。値の選び方は 6 章と 7 章の代表値に従う。
- 操作と対象は、画面の文言（「追加」「削除」、入力欄「タスク名」）と API のメソッド・パスで示す。画面の要素の取得方法（ラベル、ロール、アクセシブルネーム）は、実装に依存しない形で書く。
- ペアワイズや状態遷移表に基づくケースは、`input` に項番（PW-xx、ST-xx）を書く。

## 5 期待結果

期待結果（`expected_result`）は、**画面・API・DB（保存データ）・ログ**のうち、そのケースで観察できるものすべてについて、合否を判定できる具体的な値で書く。

| 観察先 | 書き方の規約 |
|---|---|
| 画面 | 表示される文言（仕様の文言を一字一句）、行数と並び、チェック状態、取り消し線（computed style の text-decoration-line）、入力欄の値、エラーの表示位置（入力欄の直下 / 画面上部）、操作可否（disabled、非表示） |
| API | HTTP ステータス、本文のキーと値（`error.code`、`error.message`）、ヘッダ（Location が付かない、WWW-Authenticate が付かない）、呼ばれた回数 |
| DB | `tasks` テーブルの行数、対象行の各列（id・title・completed・createdAt）、DB ファイルの SHA-256（破損・保存失敗のケースで書き換わっていないことの確認）。表名は実装に合わせる |
| ログ | backend の標準出力（pino 形式の JSON 行）の `statusCode` と `level`（50 以上が error）。error の行にエラーコード（STORAGE_FAILURE・DATA_CORRUPT）が識別できること |
| 通知 | **本アプリに通知はない**（仕様 §01 の対象外）。通知の期待結果は書かない |
| 連携 | **外部サービス連携はない**。frontend と backend の連携は API の期待結果として書く（`/api` の中継を含む） |

- 「正しく」「適切に」「正常に」「問題なく」「期待どおり」のような**判定できない語を使わない**。
- ログの期待値は、運用の確認項目（docs/11-monitoring.md）と同じく、**backend の実装に合わせて確定する運用要件の案**である。実装が異なる場合は、ケースの期待結果と運用要件を合わせて改訂する（変更手順は 14 章）。
- 暫定期待値は、期待結果に「暫定」と未決 ID（UNK-xxx）を明記し、合否に含める部分と含めない部分を分ける。

### 6.2 設計の考え方

- **代表値**: タイトルの境界値セット（DS-003）は、長さ 0・1・99・100・101・100,000、絵文字・結合文字のコードポイント数、前後空白、改行を式で定義する。状態を作る標準データ（DS-002）は、未完了 2・完了 1 の 3 件で、createdAt はすべて別時刻とする。同時刻（DS-004）は createdAt を同一にして保存順を固定する。
- **生成**: 固定ファイルを持たず、**テストコードの中で生成**する（`String.prototype.repeat`、Unicode エスケープ、`seedTasks()` による SQLite への直接投入）。同一ミリ秒の createdAt は API では作れないため、DB へ直接投入する。
- **匿名化**: すべて架空の日常語・連番で、**個人情報（氏名・メールアドレス・電話番号）を使わない**。本アプリは利用者情報を持たないため、本番データの持ち込み・マスキングは不要。実機試験の記録には機種名と OS の版だけを書く。
- **初期化**: ケースごとに専用の一時ディレクトリに新しい SQLite を作り、データセットを投入してから backend を起動する。ブラウザコンテキストもケースごとに新規にする。
- **後始末**: 7 章のとおりケースの `cleanup` 列に書く。一時ディレクトリごと削除し、compose はプロジェクト単位で `down -v` する。書込み不可の環境（DS-008）は `finally` で権限を戻してから削除する。

## 7 境界・最大数

入力規則の数値は、タイトルの長さ 1〜100（Unicode コードポイント、前後空白除去後）だけである。最小・下限前後・上限前後・最大超過・大容量を次の表のとおり設計した。

| 区分 | 境界の定義 | 代表値 | ケース |
|---|---|---|---|
| 最小 | title の長さ 0（断る）と 1（受け付ける） | ""、"a"、"あ" | TC-021, TC-022, TC-032 |
| 下限前後 | 0 / 1 / 2 文字（下限 1）。前後空白除去後に空になる値も含む | ""、"   "、"a"、"ab" | TC-021, TC-022, TC-016, TC-032, TC-026 |
| 上限前後 | 99 / 100 / 101 コードポイント（上限 100） | a×99、a×100、a×101、😀×100、😀×101 | TC-023, TC-024, TC-018, TC-017, TC-030, TC-031, TC-025 |
| 最大超過 | 101・102・100,000 コードポイント | a×101、a×102、a×100000 | TC-024, TC-031, TC-017 |
| 大容量 | 1,000 件の一覧、20 件の並行追加、10 万文字の入力 | DS-006（1,000 件）、並行 20 件 | TC-073, TC-074, TC-064, TC-031 |
| コードポイント数え | UTF-16 長と異なる数え方（サロゲートペア、結合文字） | 😀×100（UTF-16 長 200）、e+U+0301×50（コードポイント 100） | TC-025, TC-030, TC-006, TC-007 |
| 前後空白 | 除去前後で長さが変わる境界 | " "+a×100+" "、"  "+a×101+"  " | TC-026, TC-034, TC-004, TC-005 |

- 値の選び方: 境界の ±1 を必ず含める（99・100・101）。コードポイントと UTF-16 長が異なる値（絵文字）を、境界の上限でも確認する（😀×100 は合格、😀×101 は不合格）。
- 長時間の条件（ソーク試験）は、個人用で常駐時間の要求がなく、本表では設計していない。必要性は docs/07-performance.md で判断する。

## 8 組合せ・状態遷移

### 8.1 ペアワイズ（追加操作）

**対象の条件**: 追加操作の入力方法（Enter キー / 追加ボタン）、タイトル種別（通常・前後空白付き・絵文字 100 コードポイント）、画面幅（360px / 1280px）、既存タスク（0 件 / 3 件）の 4 因子。

**削減の根拠**: 全組合せは 2×3×2×2 = 24 通り。**すべての 2 因子の組合せ（ペア）を少なくとも 1 回含む最小規模の 6 行**に削減した（タイトル種別が 3 水準のため、6 行が下限）。入力方法・画面幅・既存件数は、送信関数の手前で合流するか、描画だけに影響し、**3 因子以上の交互作用の見込みは低い**ため、ペアワイズで十分と判断した。ペアの網羅は、提出前に機械的に確認した（6 因子対のすべてで、全水準の組合せが現れる）。

| 行 | 追加の入力方法 | タイトル種別 | 画面幅 | 既存タスク | ケース |
|---|---|---|---|---|---|
| PW-01 | Enter キー | 通常（買い物） | 360px | 0 件 | TC-002 |
| PW-02 | 追加ボタン | 通常（買い物） | 1280px | 3 件 | TC-003 |
| PW-03 | Enter キー | 前後空白付き | 1280px | 3 件 | TC-004 |
| PW-04 | 追加ボタン | 前後空白付き | 360px | 0 件 | TC-005 |
| PW-05 | Enter キー | 絵文字 100 コードポイント | 360px | 3 件 | TC-006 |
| PW-06 | 追加ボタン | 絵文字 100 コードポイント | 1280px | 0 件 | TC-007 |

優先度で削減した組合せ: 全組合せのうち 18 通りは実施しない。高リスクの値（絵文字の上限、前後空白）は、2 つの入力方法と 2 つの画面幅のすべてに少なくとも 1 回現れる。

| ST-02 | 未完了 | 完了にする（PATCH completed=true） | 完了 | 許可 | 200 | TC-008, TC-009 |
| ST-03 | 完了 | 未完了に戻す（PATCH completed=false） | 未完了 | 許可 | 200 | TC-008, TC-009 |
| ST-04 | 完了 | 同じ値で PATCH（completed=true） | 完了（変化なし） | 許可（冪等） | 200 | TC-009 |
| ST-05 | 未完了 | 同じ値で PATCH（completed=false） | 未完了（変化なし） | 許可（冪等） | 200 | TC-009 |
| ST-06 | 未完了 | 削除 | 削除済み | 許可 | 204 | TC-013, TC-015 |
| ST-07 | 完了 | 削除 | 削除済み | 許可 | 204 | TC-014 |
| ST-08 | 削除済み | 完了にする / 未完了に戻す / 削除 | 削除済みのまま（復活しない） | 禁止 | 404 TASK_NOT_FOUND | TC-011 |
| ST-09 | 未存在（有効な形式の未登録 id） | 完了にする / 削除 | 未存在のまま | 禁止 | 404 TASK_NOT_FOUND | TC-011 |
| ST-10 | 未完了 / 完了 | id・title・createdAt を含む PATCH 本文 | 変化なし | 禁止 | 400 INVALID_REQUEST | TC-010 |
| ST-11 | -（id の形式が不正） | abc、123 を id に指定した PATCH / DELETE | 変化なし | 禁止 | 400 INVALID_REQUEST | TC-012 |

画面状態の遷移（初期 → 読み込み中 → 一覧 / 0 件 / 保存エラー / データ破損）は 9 章の表で期待動作を定義する。保存エラーからは、同じ操作の再試行で一覧へ復帰でき、データ破損からは復帰しない（再読込でも同じ表示）。

## 9 初期・Empty・Loading・Error

画面状態ごとに、再現条件と期待動作を定義する。権限なしは、認証・認可を持たないため状態が存在しない（非適用）。

| 画面状態 | 再現条件 | 期待動作 | 観点 | ケース |
|---|---|---|---|---|
| 初期 | 保存データがない状態で初回起動 | 「タスクはありません」、入力欄は空、エラー領域は空。GET が 200 で空配列 | VIEW-043 | TC-056, TC-076, TC-044 |
| 0 件 | 全件削除後（初期と別経路） | 「タスクはありません」。再読込後も同じ。DB は 0 行 | VIEW-044 | TC-014, TC-056 |
| 読み込み中 | 一覧の取得が遅延している間 | 取得前に「タスクはありません」を表示せず、「読み込み中…」を表示して入力・追加を無効にする（UNK-005 で確定） | VIEW-067 | TC-057 |
| エラー（入力） | 検証違反の入力 | 入力欄の直下に該当文言。一覧・DB は変化なし | VIEW-045 | TC-016, TC-017, TC-019 |
| エラー（保存失敗） | API 503・通信断・backend 停止 | 画面上部に「保存できませんでした。もう一度お試しください」。操作は未反映、追加時は入力値を保持 | VIEW-068 | TC-045, TC-046, TC-047, TC-048, TC-049 |
| エラー（一覧取得失敗） | 一覧取得の接続失敗 | 0 件と誤認させない。画面上部に保存失敗の文言を出し、入力・追加を止めて「再読み込み」ボタンを表示する（UNK-005 で確定） | VIEW-069 | TC-058 |
| エラー（データ破損） | DATA_CORRUPT（HTTP 500） | 「保存データを読み込めませんでした」。操作を停止し、「タスクはありません」を出さず、ファイルを上書きしない | VIEW-047 | TC-055, TC-052 |
| 権限なし | （該当なし） | 認証・認可を持たないため状態が存在しない。403 などは返らないことを API ケースで確認する | VIEW-046（非適用） | TC-059（401・403 が返らない確認） |

読み込み中と一覧取得失敗の表示は仕様に定めがなく、UNK-005（2026-10-11 解決）で確定した。遅延の再現は、固定時間の遅延ではなく「応答を保留して解放する」方式で行う（TC-057・TC-063）。

## 10 異常・障害・復旧

通信失敗・外部停止・再試行・部分成功・復旧の 5 要素を設計する。本アプリに外部サービスはなく、**外部停止は backend の停止**として扱う。

| 要素 | 再現方法 | 期待動作 | ケース |
|---|---|---|---|
| 通信失敗（network_failure） | ブラウザのオフライン、接続中断 | 保存失敗の文言、入力値保持、未反映、復帰後の同じ操作で成功 | TC-048, TC-058 |
| 外部停止（external_down） | backend プロセス・コンテナの停止 | 保存失敗の文言、health が 502/504（外形監視で検知）、再起動後に成功 | TC-049, TC-077 |
| 再試行（retry） | 失敗後に入力値を変えず同じ操作 | 1 件だけ追加され重複しない。保存失敗（書込み不可）の解除後も同じ POST が成功 | TC-048, TC-049, TC-050 |
| 部分成功（partial_success） | 書込み不可環境での POST / PATCH / DELETE | 503 STORAGE_FAILURE。DB のバイト列・行内容が失敗前と同一（途中まで反映されない） | TC-050, TC-051, TC-053 |
| 復旧（recovery） | backend 再起動、コンテナ再起動、書込み権限の復旧 | 復旧後の整合: 件数・内容・並び順が一致し、重複・欠落がない | TC-042, TC-043, TC-049, TC-050 |
| データ破損 | DS-007 の破損 DB | DATA_CORRUPT。起動を繰り返してもファイルを書き換えない | TC-052, TC-053, TC-054, TC-055 |

障害の注入方法は、画面側の失敗を Playwright の `page.route`・`setOffline`（DS-012）で、backend 側の失敗を書込み不可環境（DS-008）・破損ファイル（DS-007）・プロセス停止で再現する。**復旧後の整合**は、復旧前後の全項目（id・title・completed・createdAt・並び順）を比較して確認する。

## 11 権限・セキュリティ

本アプリは認証・認可を持たない（仕様 §01）ため、**権限の確認を「画面の非表示」ではなく、直接 URL・API の操作、不正入力、XSS で代替する**。画面を通さない API 直接操作でも、backend が入力検証・id 検証を適用することを確認する。

| 観点 | 本アプリでの扱い | ケース |
|---|---|---|
| 直接 URL・API（画面を迂回） | 認証・認可がないため、画面の非表示ではなく backend の入力検証・id 検証・エラー形式が保護の本体 | TC-059, TC-031, TC-032, TC-035, TC-036, TC-012 |
| 権限昇格・他人のデータ | ロール・利用者の区別がなく非該当（1 インスタンス = 1 人用） | ケースなし（VIEW-023・VIEW-024 は非適用） |
| セッション・トークン期限 | セッション・Cookie・トークンを持たず非該当。Cookie が発行されないことを確認 | TC-059 |
| 不正入力（XSS） | タイトルを HTML として解釈しない（§07） | TC-061, TC-062, TC-060 |
| 不正入力（インジェクション） | SQLite へのパラメータ化。SQL 断片が文字列として保存される | TC-060 |
| 依存・イメージの脆弱性 | 動的ケースの対象外。成果物 08 の静的検査で扱う | ケースなし（VIEW-029 は非適用） |

認証を後から導入する場合は、02 の 11 章の非適用行（利用者・権限・セッション）を適用へ戻し、権限昇格・トークン期限のケースを追加する。

## 12 独立性・後始末

- **ケース間の独立**: 各ケースは専用の一時 DB・専用のポート・新規のブラウザコンテキストを使い、他のケースが作った状態に依存しない。実施順を入れ替えても、もう一度実施しても同じ結果になる。
- **並列実行**: DB ファイル・ポート・ブラウザコンテキストをケースごとに分けているため、unit・api・e2e（compose 以外）は**並列に実行しても汚染しない**。compose を使うケース（`@compose` タグ）は、専用のプロジェクト名で隔離したうえで、公開ポートと負荷の都合から直列（workers=1）で実行する。
- **後始末**: すべてのケースの `cleanup` 列に書く。一時ディレクトリ（DB）の削除、backend プロセスの停止、ブラウザコンテキストの破棄、compose の `down -v`。失敗しても残らないよう、テストフレームワークの終了処理（`afterEach` / `finally`）で行う。
- **再実行**: 後始末が済んでいれば、同じケースを何度でも実施できる。固定ポートを使わず、固定の絶対パスを使わない。
- 手動ケースは、テスト用の backend と一時 DB を削除し、端末のブラウザのサイトデータを消去する。
