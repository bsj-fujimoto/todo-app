この文書は、v1.0.0 までに見つかった欠陥・不安定なテスト・誤検知から、**欠陥が作り込まれ、見逃され、検知が遅れた仕組み**を特定し、開発工程・標準・自動化の何をいつ変えるかを決める。
目的は仕組みの改善であり、人やロールを評価することではない（analysis-14）。**数字はすべて出典（パス・Issue・PR・run・git）を付け、2026-10-12 に CSV・Issue・git から数え直した。**

## この文書の結論

- **母数は欠陥 10 件・観測は 1 日未満**（起票は 2026-10-11T06:40Z〜12:51Z の 6.2 時間）。**傾向（Trend）は言えない。** 割合には信頼区間を付け、事例の分析を主にする（analysis-05）。
- **共通原因を 4 つ**特定し、それぞれ複数の欠陥で確かめた（analysis-07）。
  - RC-1 設計時に「資源の寿命・設定の優先順位・件数依存のコスト」を書き出す観点が無い（DEF-005・DEF-016・DEF-031、受容の DEF-033）。
  - RC-2 テストの期待値（動作・しきい値）が、仕様や SLO でなく実装の挙動や暫定値に置かれた（DEF-011・DEF-015・DEF-025・DEF-037）。
  - RC-3 製品の変更が、隣の検査資産（ケース・監視）へ波及する経路が人の記憶頼み（DEF-011・DEF-036。DEF-016 は部分的）。
  - RC-4 検出は、その検出層が初めて動いたときに集中する。検出の遅れは、コードの質でなく層の稼働時期で決まっている可能性がある（DEF-016・DEF-031・DEF-036 で確認。仮説）。
- **10 件中 9 件は、実際に見つかった工程より前の工程で見つけられた可能性がある**（前倒し可能率 9/10、95% 区間 約 60〜98%。起票者の事後判断）。ただし、前倒し先の仕組み（単体・compose の試験）が当時あったのは 3 件だけで、6 件は**仕組み自体が無かった**（設計レビュー・PR レビュー・層の役割の規約など。analysis-09）。
- **本番・利用者への流出は 0 件**だが、本番が無いので意味は限定的。混入した PR のマージ後に見つかった欠陥は **7/10**（95% 区間 約 40〜89%）、PR の中で見つかったのは 3/10（analysis-09）。
- **9/10 の欠陥に、テスト・監視側の原因または寄与がある**のに、原因分類が test なのは 2 件だけ（単一の分類では見えない。analysis-07・analysis-03）。
- **できていないこと（正直に）**: ①再発率・流出率の「改善」は測れない（0/7、観測 1 日未満）。②効果指標は初回の値を手で数えただけで、定期計測は無い（ACT-020）。③観点表への反映は未実施（採否は ACT-017。この文書の担当外のため）。④施策の優先順位は単独のオーナーの判断で、チームでの合意ではない。⑤再分析（2026-11-12）はまだ実施していない。
- **施策**: 新規 7 件（ACT-016〜ACT-022）を [docs/data/actions.csv](data/actions.csv) に追記した。既存の施策（ACT-002・ACT-003・ACT-006・ACT-007・ACT-011・ACT-012）と対応付けた（analysis-11）。

## 前提と読み方

- **対象と体制**: ToDo アプリ（frontend nginx + backend Fastify/SQLite）。実装・テスト・監視はすべて AI エージェントが書き、リポジトリオーナーが PR をマージする運用（[ADR-0004](adr/0004-single-maintainer-governance.md)）。マージ済み 30 PR に付いた GitHub のレビューは 6 件（`gh pr list --state merged`）。したがって「実装担当が人か AI か」は定数で、比較できない（analysis-08）。
- **数えた時点**: 2026-10-12。欠陥表は Issue の取得物（`docs/evidence/github/SOURCE.json` の `captured_at` = 2026-10-11T16:19:01Z、head 49c40cc）から生成されている。v1.0.0 の公開は 2026-10-11T15:43Z（タグ）。時刻は UTC（JST は +9 時間）。
- **材料**: 欠陥表 [defects.csv](data/defects.csv)、Issue（`gh issue list --state all`）、実施表 [executions.csv](data/executions.csv)、[cases.csv](data/cases.csv)、[perspectives.csv](data/perspectives.csv)、[traceability.csv](data/traceability.csv)、検出表 [findings.csv](data/findings.csv)・[security/triage.yaml](../security/triage.yaml)、flaky 台帳 [quality/flaky-ledger.yaml](../quality/flaky-ledger.yaml)、incident #36、PR・commit の履歴。関連文書: [04](04-regression.md)・[08](08-inspection.md)・[09](09-test-execution.md)・[11](11-monitoring.md)。
- **サンプルの小ささ**: n = 10 の割合は区間が広い（例: 3/10 は 11〜60%）。本書の割合は「観察された事実」であり、「母集団の率」ではない。20 件に満たない間は、割合を目標判定に使わない（analysis-12・ACT-021）。
- **用語**: 「混入工程」は欠陥を作り込んだ工程、「検出工程」は見つけた工程、「検出可能だった工程」（`could_detect_at`）は Issue の起票者が事後に判断した、より早く見つけられた工程（事後判断なので後知恵が入る）。

## analysis-01 分析目的・問い

**結論**: v1.0.0 までの欠陥から「どの工程で作り込み、どの工程で見つかり、なぜ前で見つからなかったか」を明らかにし、**フェーズ2（期限機能）の設計に入る前に、直す仕組みを決める**分析である。

**目的（goal）**

- 事業目標との結び付き: [01 の plan-01](01-test-plan.md) の目的は「利用者が入れたタスクが黙って失われないこと」「画面は成功に見えるのに保存されていないことが無いこと」。その品質目標のうち、Q-02（critical・major の未修正 0）、Q-03（minor の未修正 5 件以下）、Q-06（ゲート対象の flaky 0）が、欠陥の作り込みと検出の遅れで揺らいだ。主因を減らせば、フェーズ2 でリリース判定（plan-12）を再び満たすための手戻りが減る。
- 分析で答える問い（比較単位を括弧内に示す）:
  - Q1 欠陥はどこに集中するか（機能・原因分類・品質特性・混入元の PR）。
  - Q2 作り込んだ工程と見つけた工程はどれだけ離れているか（混入工程 × 検出工程）。
  - Q3 複数の欠陥にまたがる共通原因はあるか（欠陥 × 要因 7 区分）。
  - Q4 欠陥は観点表・ケース・監視のどこで守れていなかったか（欠陥 × 観点・ケース・監視）。
  - Q5 flaky・誤検知は何が原因で、同じ原因が繰り返されたか（TC-073・TC-074・MON-008）。

**仮説（hypothesis）と検証計画**

| 仮説 | 内容 | 検証の方法 | 棄却の条件 | 確認日 |

## analysis-03 分類体系

**結論**: 欠陥の分類は 6 列（機能・品質特性・原因分類・混入工程・検出工程・重大度）で、**語彙は [build-defects の VOCAB](../scripts/evidence/lib/defects.mjs) に定義され、取り込み時に強制される**（語彙外は欄が空になり、「必須項目が無い」として生成が失敗する）。定義書はこの章で、意味の定義は不足している箇所を明記する。

**強制される箇所**: ① 入力: [Issue テンプレート](../.github/ISSUE_TEMPLATE/defect.md)に、語彙を HTML コメントで書いてある。② 取り込み: `extractFields`（`onlyKnown`）が語彙外を空にし、`problemsOf` が必須項目の欠けを Issue 番号付きで報告して失敗する。③ 生成後: `checkDefectRows` が全列の語彙を再検査する。④ CI: `check-evidence.mjs`。

| 列 | 語彙（`VOCAB`） | 定義（本書が置く） | 本表での使われ方（10 件） |
|---|---|---|---|
| 重大度 `severity` | critical / major / minor / trivial | [01 の plan-12](01-test-plan.md) の定義: critical = データ損失・破損データの自動上書き・保存結果の黙った不一致・セキュリティ侵害。major = 主要機能が使えない・画面と保存の食い違い・入力値の消失。minor = 回避できる・体感や計測の揺れ。trivial = 見た目・記述。別名（high・medium・low など）は取り込み時に寄せる | major 2・minor 8（critical・trivial は 0） |
| 機能 `function` | add / list / toggle / delete / validation / storage / api / ui / infra | add・list・toggle・delete・validation = 利用者の操作。ui = 画面。storage = 保存層。api = HTTP の層。infra = 上記以外の構成・監視・計測・CI。**monitoring・perf の語彙は無く infra に寄せる**（DEF-036・DEF-033） | infra 3・storage 2・api 2・add 1・toggle 1・ui 1 |
| 品質特性 `quality_attr` | functional / reliability / usability / security / performance / compatibility | ISO/IEC 25010 の品質特性のうち、本アプリに関わる 6 つ（本書の整理） | reliability 4・performance 3・functional 2・security 1 |
| 原因分類 `cause_class` | requirements / design / implementation / review / test / environment / process | 根本原因が最初に生まれた場所を **1 つだけ**選ぶ。複数の要因は analysis-07 の表（本書）で扱う。process = 手順・規則・テンプレートの不備 | design 4・implementation 3・test 2・process 1（requirements・review・environment は 0） |
| 混入工程 `injected_phase` | requirements / design / implementation / test / environment / review / unit / api / e2e / regression / monitoring / production | 欠陥を作り込んだ工程。検出工程と同じ語彙を使う | implementation 4・design 3・test 3 |
| 検出工程 `detected_phase` | 同上 | 見つけた層・手段。unit・api・e2e・regression は自動テストの層、monitoring は外形監視、review はレビュー・静的解析、test は専用のテスト（負荷試験など） | api 2・e2e 2・regression 2・monitoring 2・test 1・review 1 |
| 検出可能だった工程 `could_detect_at` | 同上（検出手段の語を優先） | 起票者の事後判断 | review 3・design 2・unit 2・test 2・e2e 1 |

**足りない定義（正直に）**: ①「`test` 工程」の二義（analysis-02）。②機能に monitoring・perf が無い。③混入工程に `process`・`review` の意味づけが無く、原因分類と食い違う（DEF-033・DEF-036）。④原因分類が 1 つだけで、副次要因を持てない。①〜④は ACT-019。**この章の定義は暫定で、語彙の変更は `defects.mjs` と Issue テンプレートの変更を伴う（本書の担当外）。**

## analysis-04 母数・正規化

**結論**: 件数をそのまま比べず、領域ごとに**変更量（行数・PR）、ケース数、実行数、期間**で割る。ただし分母の性質が違うため、**領域間の比較には使わない**（各行に理由を書く）。利用量（リクエスト数・利用者数）での正規化は、本番も利用者も無いため**できない**。

**正規化する指標（metrics）**

| 指標 | 式 | 値 |
|---|---|---|
| 製品コードの欠陥密度 | 製品コードに混入した欠陥（DEF-005・DEF-006・DEF-011・DEF-015・DEF-031）÷ 製品コードの行数（KLOC） | 5 件 ÷ 1.349 KLOC = **3.7 件/KLOC**（DEF-016 は docker-compose.yml の設定で、行数に含めない） |
