# ADR-0005: 機能層の性能テストは「番兵」にし、SLO の本判定は perf 層で行う

- 状態: 採用（2026-10-11）
- 決定者: QA リード（性能テストの層の役割分担）、バックエンド担当・フロントエンド担当（しきい値の実装）、プロダクトオーナー（PR #38 のマージをもって承認。フェーズ1は AI が代行マージ）
- 関連: Issue #25（TC-073 が共有ランナーで不安定。DEF-025）、Issue #37（TC-074 が同種）、PR #38、`perf/slo.yaml`、`quality/flaky-ledger.yaml`、`docs/data/cases.csv` の TC-073・TC-074

## 背景

機能テスト層（api 層の TC-073、e2e 層の TC-074）に、性能の暫定しきい値（一覧 p95 500ms・追加 p95 300ms、各操作の反映 1,000ms・表示完了 2,000ms）を絶対時間で置いていた。
GitHub-hosted の共有ランナー（ubuntu-24.04）は負荷が変わるため、**同じコードで pass と fail が混在**した。

- Issue #25: PR #8 の CI（run 38123866985）で TC-073 の追加 p95 が 452.0ms となり、暫定しきい値 300ms を超えた。同じ変更を含む他の run は成功。
- Issue #37: main への push の CI（run 38140205187）で TC-074 の追加の反映が 1054ms となり、しきい値 1000ms を超えた。同じ run の他の値（表示完了 364ms・完了切替 127ms・削除 205ms）と、直近 9 回の追加（287〜411ms）は通っていた。10 回中 1 回（0.1）。

どちらもアプリの退行ではなく、**共有ランナーの負荷と、expect の再試行間隔（100 → 250 → 500 → 1000ms）の粒度**による偽陽性だった。main の CI が不定期に赤くなり、リリース判断の信頼性を下げた。

## 決定

- **機能層（TC-073・TC-074）は「桁が違う劣化を見つける番兵」**とする。CI（環境変数 `CI` あり）では**しきい値を 3 倍**にする（TC-073: 一覧 1,500ms・追加 900ms、TC-074: 表示完了 6,000ms・各操作 3,000ms）。ローカルは従来の厳しい値のままにする。実測値は常に観察値に残す。
- **SLO の本判定は perf 層**（`.github/workflows/perf.yml` の k6 と画面計測。値は `perf/slo.yaml`、判定は `scripts/perf/verdict.mjs`）が行う。warm-up と外れ値の除外、3 反復の平均と信頼区間、baseline との比較（既定 +20%）を持つ。
- `retry` で隠さない（Playwright は `retries: 0`）。直るまでの間は `quality/flaky-ledger.yaml` に**期限付き（since から 30 日以内）**で隔離し、日次の全件回帰では実行し続ける。
- TC-073・TC-074 の必須区分は「任意」（リリース判定に含めない）。リリース可否に使う性能の判定は perf 層の SLO 達否（docs/01-test-plan.md の plan-12）。

## 影響

- main の CI が計測の揺れで赤くなる偽陽性を減らす。性能の合否は、揺れを統計で扱える perf 層に一本化される。
- **限界（正直に）**:
  - 3 倍にした番兵は、2〜3 倍程度の劣化は見逃す。小さな退行は perf 層（baseline +20%）が見るが、perf 層は週次・リリース前・手動で、**PR ごとには動かない**。
  - 3 倍という係数は CI の通常値の分布（追加 287〜411ms）から決めた経験則で、統計的に導いた値ではない。
  - perf 層の実測は開発機（`local:darwin-arm64`）のもので、**GitHub-hosted runner での baseline は未取得**（`perf/environment.md`）。runner 上の SLO 判定は、初回の `perf.yml` 実行結果を baseline に追記するまで比較対象が無い。
  - 隔離の台帳には TC-073・TC-074 が残っている（期限 2026-11-10）。週次の `--repeat-each=3` で混在が無いことを確認できたら外し、#25 を閉じる（#37 は修正済みでクローズ）。
- 同じ考え方を他の絶対時間の判定にも使う: 計測の揺れが入る判定は、機能層では番兵に、本判定は専用の層に置く。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| しきい値を SLO と同じ値のまま retry する | 失敗を隠し、retry を許すと本物の劣化と区別できない（`retries: 0` の方針に反する） |
| 機能層の性能テストを廃止する | 桁違いの劣化（全件描画の崩れなど）を PR で見つける安価な番兵が無くなる |
| 相対比較（直前の run との比）にする | 共有ランナーでは直前の run も揺れる。baseline を持つ perf 層の役割と重なる |
| 専用ランナー（self-hosted）で機能層の性能も判定する | 公開リポジトリで self-hosted を使うのはセキュリティ上のリスクが大きい。運用の手も足りない |
