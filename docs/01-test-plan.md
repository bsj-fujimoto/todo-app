この計画書は、限られた時間と人員をどのリスクへ配分し、何を根拠に「リリースしてよい」と判断するかを合意するための文書である。
**v1.0.0 のリリース（2026-10-12 JST）の後に起こした**。リリース時点で基準を文書にしていなかったが、基準そのものは `ci.yml`・`release.yml`・`security.yml` のゲートと [03 テスト仕様書](03-test-spec.md) の 2 章に実装されている。本書はそれを成文化し、plan-12 の末尾で v1.0.0 の実績を基準に当てはめて検証した（後付けであることを隠さない）。

## この計画書の結論

- **対象**: ToDo アプリ フェーズ1（仕様 v1.1。1 画面・個人利用・サーバー保存）。フェーズ2（期限設定）は別紙 `docs/draft/phase2` で固める予定で、本書の範囲外（plan-02・plan-03・plan-10）。
- **配分**: リスク 16 件のうち high は 3 件（データ損失、保存失敗時の画面と保存の乖離、破損データの自動上書き）。high 由来の 31 ケースはすべて必須とし、必須は 77 ケース中 66 件（plan-04）。
- **自動化**: 77 ケース中 75 件（97.4%）が自動。手動は実機の 2 件（TC-071・TC-072）で、**未実施**（plan-05・plan-12）。
- **リリース判定**: 必須ケース 100% 合格、critical・major の未修正 0、minor の未修正 5 件以下（全件に Issue・回避策・期限）、必須の未実施 0、残存リスクは期限・責任ロール・補完統制つきで受容（plan-12）。
- **できていないこと（要約）**: 実機（iOS Safari・スクリーンリーダー）未実施、GitHub-hosted runner での性能 baseline 未取得、長時間（2 時間以上）の soak 未実施、運用の実績日数が短い（4 日未満）ため外形監視の稼働率・nightly の傾向は評価できない、Ruleset が未適用（ADR-0004）、独立した第二のレビュアーがいない（plan-09）。

## plan-01 目的・品質目標

**結論**: v1.0.0 を出してよいかを、数値で判断する。失敗させたくないのは「利用者が入れたタスクが黙って失われること」と「画面は成功に見えるのに保存されていないこと」。目標は 12 項目（Q-01〜Q-12）で、いずれも測れる値と出典を持つ。

**目的（purpose）**

1. 追加・完了切替・削除の結果が、再読込・backend 再起動・コンテナ再作成を越えて残る（AC-06。RISK-001）。
2. 保存に失敗したとき、画面は反映せず、入力値を保持し、決められた文言を出す（AC-07。RISK-003）。保存データが壊れているとき、自動で上書きしない（RISK-004）。
3. 不正な入力（空白のみ・101 文字・改行）が保存されず、100 文字ちょうどや絵文字入りの有効な入力が拒否されない（AC-02。RISK-002）。
4. 停止・DB 異常に運用側が気づける（health と外形監視。RISK-011）。
5. 上記をリリースのたびに、同じ手順で、機械的に確認できる（回帰・証跡）。

**低減するリスク（risks_to_reduce）**: [02 の 2 章](02-test-perspectives.md)と `docs/data/risks.csv` の 16 件。重点は high の 3 件。

| 区分 | リスク | 本計画での扱い |
|---|---|---|
| high（3） | RISK-001 データ損失、RISK-003 保存失敗時の画面と保存の乖離、RISK-004 破損データの自動上書き | 全ケースを必須。unit・api・e2e・compose・外形監視（MON-003・MON-013）の多層で確認（plan-04） |
| medium（7） | RISK-002 検証抜け、RISK-005 XSS、RISK-006 並び順、RISK-007 モバイル・a11y、RISK-008 契約逸脱、RISK-011 停止に気づけない、RISK-013 二重送信 | 必須ケースを持つ。RISK-005 は CodeQL・ZAP も併用 |
| low（6） | RISK-009 依存・コンテナの脆弱性、RISK-010 件数増加時の性能、RISK-012 将来の移行、RISK-014 ブラウザ差異、RISK-015 コンテナ起動、RISK-016 認証なし前提の逸脱 | RISK-009 は静的検査、RISK-010 は perf 層、RISK-012 はフェーズ2、RISK-016 は受容（plan-12） |

**目標の根拠（過去の障害・実測）**

- **実不具合**（`docs/data/defects.csv`、GitHub Issue）。この 4 件は、いずれも「テストを回して見つけ、修正し、回帰ケースに戻した」もの。
  - **#5（DEF-005、major）**: 書込み不可で開いた SQLite 接続が、権限を戻しても書込み不可のまま（TC-050）。保存失敗からの復旧という、データ保護の中核（RISK-001・RISK-003）で出た。→ Q-02（major を残さない）と、保存系を high にした根拠。
  - **#6（DEF-006、major）**: 追加の送信中に打った次の入力が、先の追加の成功で消える（TC-061・TC-063）。成功後に入力欄を無条件で空にしていた。入力値の保持（REQ-023）に反する。→ Q-02。
  - **#11（DEF-011、minor）**: 完了切替の通信中にチェックボックスが反転して見える（TC-008・TC-046）。「成功を確認してから反映」（REQ-004）に反する。→ RISK-003 を high とした根拠。
  - **#15（DEF-015、minor）**: 本文サイズ超過の応答が RST で失われ、テストが不安定（TC-031）。→ Q-06（flaky 0。`retries: 0` で隠さない）。
  - 4 件はいずれも pre-1.0.0 の CI・テスト実施中に見つかり、1.0.0 までに修正済み。**リリース後の欠陥は 0 件だが、運用日数が短く（4 日未満）、リリース後に欠陥が出ていないことは品質の証拠として弱い**。
- **flaky の実例**: #25（TC-073、共有ランナーで追加 p95 が 452.0ms）、#37（TC-074、追加の反映が 1054ms）。→ Q-06 と、性能を番兵と本判定に分ける決定（[ADR-0005](adr/0005-functional-layer-perf-sentinel.md)）。
- **性能の実測**（[perf/analysis.md](../perf/analysis.md)）: 想定負荷では SLO に大きな余裕がある一方、限界は約 100〜150 req/s（1,000 件）、10,000 件では約 30 req/s で、原因は書込みでも全行を読む設計（#31）。→ Q-07 の適用範囲を 1,000 件に置き、10,000 件は観測値にとどめる。
- **未実施の根拠**: Q-12 のように、実績が無い目標は「評価できない」と書き、達成したことにしない。

## plan-06 テストレベル・タイプ

**結論**: 単体・結合・システム・受入と、機能・非機能の担当を下表に固定する。担当はロール名で、AI エージェントが実作業を行い、人（リポジトリオーナー）はマージで承認する。

**単体テストの担当（unit）**／**結合テストの担当（integration）**／**システムテストの担当（system）**／**受入テストの担当（acceptance）**／**非機能テストの担当（nonfunctional）**／**担当の役割名（owner_role）**

| レベル・タイプ | 何を確かめるか | 実行の場 | 担当ロール | 次のレベルへ持ち越すもの |
|---|---|---|---|---|
| 単体（unit） | 検証関数の境界値・数え方、描画関数のエスケープ。DB・ブラウザ無し | `backend/test/unit`、`frontend/test/unit`（143 テスト） | バックエンド担当・フロントエンド担当 | 画面・HTTP を通した振る舞いは結合へ |
| 結合（integration） | backend の入力検証・状態遷移・保存失敗・データ破損・並行・health を、専用 SQLite と HTTP で。契約適合 | `backend/test/api`（74 テスト）、contract（8 テスト） | バックエンド担当（実装）、QA 担当（ケース） | 画面と backend の組合せはシステムへ |
| システム（system） | 画面操作を通した受け入れ条件・画面状態・a11y・互換、compose の実 nginx・コンテナ・ボリューム | `e2e/tests`（43 テスト、4 project）、`e2e/compose`（4 テスト） | QA 担当（ケース）、フロントエンド担当（実装） | 実機・本番相当は受入・運用へ（未実施） |
| 受入（acceptance） | AC-01〜AC-07 をケース化して確認（上の e2e・api）と、リリース判定 | AC は e2e・api（[03 の 1.2](03-test-spec.md)）。リリース判定は plan-12 | QA リード（判定案）、プロダクトオーナー（承認）。業務部門・利用者による受入は**無い**（1 人用でオーナーが利用者を兼ねる） | 実機の受入（TC-071・TC-072）は未実施として受容 |
| 機能 | F-01〜F-04、入力検証、保存 | 上の unit・api・e2e | 同上 | — |
| 非機能: 性能 | SLO（負荷・画面の表示完了） | k6・Lighthouse（`perf.yml`）、機能層は番兵（[ADR-0005](adr/0005-functional-layer-perf-sentinel.md)） | バックエンド担当（API）、フロントエンド担当（画面） | 本番相当の性能は持ち越し（plan-07） |
| 非機能: a11y・互換 | ラベル・キーボード・360px、3 ブラウザ | axe（TC-067〜TC-069）、`@cross-browser`（TC-001・TC-056・TC-070） | フロントエンド担当、QA 担当 | 読み上げ・実機は手動へ（未実施） |
| 非機能: セキュリティ | 脆弱性・秘密情報・ライセンス・DAST | `security.yml` | セキュリティ担当 | 認証は対象外（api-02） |
| 非機能: 運用・可観測 | health、外形監視、通知、runbook | `synthetic.yml`、`monitoring/` | 運用（SRE）担当 | 本番の可用性は持ち越し |

**レベル間の境界（何を上位に持ち越すか）**: 下位で確かめた規則（検証・状態遷移）は上位で重ねて確かめず、上位は「結び付き」（画面と API の整合、永続化の越境）に絞る。たとえば検証の境界値は unit で網羅し、e2e は代表値で画面表示を確かめる。

## plan-09 体制・責任・承認

**結論**: 6 つの責務すべてに担当ロールを置いた。ただし**実態は単独のリポジトリオーナーと AI エージェントで、ロールはすべて兼務**。不在時の代理は置けず、レビューに第二の人の目は無い。承認は PR のマージをもって行う。

| 責務 | 担当ロール | 実態（正直に） |
|---|---|---|
| **テストケースを作る人（creation）** | QA 担当（QA リードが方針） | AI エージェントが作成（docs/02・03、`docs/data/cases.csv`）。人は PR で確認 |
| **テストを実行する人（execution）** | 自動: GitHub Actions（バックエンド・フロントエンド担当が実装と保守）／手動: QA 担当 | 自動は CI が実行し、結果は JUnit・観察値として残る。手動 2 件は**未実施** |
| **レビューする人（review）** | QA リード（文書・ケース）、開発リード（実装の PR）、セキュリティ担当（検査・依存） | 実際は作成者と同じ主体の兼務で、**独立したレビューはできていない**。本書の「レビュー」も未実施。CI（lint・テスト・セキュリティ検査・docs-check）が機械的な第二の目になっている |
| **仕様の疑問に答える人（spec_decision）** | プロダクトオーナー（仕様）。UNK ごとに決定者のロールが `resolution` に残っている（UNK-001・UNK-007: QA リード、UNK-004〜UNK-006・UNK-008: 開発リード、UNK-003: プロダクトオーナー） | 未決 8 件中 7 件が resolved、1 件が open（UNK-002、期限 2026-10-16） |
| **不具合の優先度を決める人（triage）** | QA リード（不具合の重大度・優先度）、セキュリティ担当（セキュリティの検出） | 重大度は defect Issue の語彙（critical・major・minor・trivial）。セキュリティは `security/triage.yaml`・`accepted-risks.yaml` に判断を残す |
| **最終承認する人（approval）** | プロダクトオーナー（リリース可否、残存リスクの受容、対象外の承認） | **PR のマージをもって承認**。フェーズ1の PR のマージはオーナーの明示許可（2026-10-11）に基づく AI の代行。フェーズ2の正本取り込み PR はオーナー自身がマージする |

**不在時の代理**: 置けない（制約）。オーナーが対応できない間は、PR のマージ・リリース・障害対応が止まる。外形監視の通知は GitHub Issue で、メンテナ 1 名 best-effort（sev1・sev2 の ack 目標 24 時間、sev3 は 72 時間）。リリース判定を代行できる人はいないため、**判定者不在のときはリリースしない**。

**合意の記録**: 本書の履歴表（plan-13）、PR の本文とマージコミット（Git 履歴は永続）、未決（UNK）の `resolution`、ADR（決定者ロールと日付）。**合意の相手が実在の別人であることは、この記録だけでは示せない**（人の確認が要る）。

| **開始** | 次の 5 つがすべて真: (1) 仕様書と `backend/openapi.yaml` が main にある。(2) 観点・ケースが確定（未解決の参照 0 = `docs-check` が成功。open の未決は担当と期限つき）。(3) main で `npm ci` と `docker compose up --wait` が成功し、health が `status: ok`・`db: ok`（TC-076）。(4) lint とユニット（`unit-api`）が緑。(5) データ DS-001〜DS-012 が生成できる | QA リード。結果は PR の CI（`ci-result`）で確認し、PR・Issue のコメントで通知 |

## plan-12 終了・リリース判定条件

**結論**: リリースは、**必須ケース 100% 合格、critical・major の未修正 0、minor の未修正 5 件以下、必須の未実施 0、残存リスクは期限・責任ロールつきで受容**の 4 つがすべて成り立つときだけ可とする。ケースの消化率だけでは判定しない（消化しても不合格なら不可、合格でも重大欠陥が残れば不可）。

**判定者**: QA リードが判定案（合否表）を作り、**プロダクトオーナーが承認する**（リリースタグの作成はリポジトリの管理者が行う。`release.yml`）。承認は PR のマージ、またはタグの作成をもって行い、独立した第二の判定者はいない（plan-09）。
