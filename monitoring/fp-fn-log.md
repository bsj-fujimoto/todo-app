# 誤検知（false positive）・見逃し（false negative）の記録

外形監視の信頼性を保つための台帳。**監視が鳴ったのに問題が無かった（誤検知）**、**問題があったのに鳴らなかった（見逃し）** を、
気づいた時点で 1 行ずつ追記する。月に 1 回（またはリリースごとに）見直し、閾値・retry・assertion・抑制ルールの変更に結び付ける。

## 運用ルール

1. 記録する契機:
   - incident Issue を調べて「問題なし」だった（誤検知）。
   - 利用者の報告・手動確認・別の監視で問題に気づいたが、外形監視は鳴っていなかった（見逃し）。
   - リリース直後の失敗を `SUP-001` が抑制した（抑制が正しかったか確認し、誤抑制＝見逃しなら記録する）。
2. 種別:
   - `FP`（誤検知）: 原因を「一時的なデプロイ起動中」「監視側の locator が古い」「timeout 不足」「runner の遅延」などに分類する。
   - `FN`（見逃し）: 何が検知できなかったか（assertion の不足、ジャーニーの欠落、実行間隔 30 分の間に発生して回復、など）。
3. 必ず「対応」を書く: 閾値の変更・assertion の追加・ジャーニーの追加・抑制ルールの調整・「対応しない（理由）」のいずれか。
   変更は PR（`monitoring/monitors.yaml` など）で行い、PR 番号を書く。
4. 誤検知率の見方（目安）: 直近 30 日の「通知した回数のうち、問題なしだった回数」。20% を超えたら retry・timeout・assertion を見直す。
   計算に使うデータは run history（artifact の `run-history.jsonl`）と incident Issue。
5. Issue との関係: incident Issue の「再発防止（還流先）」で「監視の追加・調整」にチェックを付けたら、ここにも 1 行追記する。

## 本リポジトリの現状（正直な注記）

- 本番が無く、外形監視の対象は GitHub Actions 上で起動した compose（リリース済みイメージまたは main の HEAD）。実利用者がいないため、**見逃しの発見源（利用者の報告）が無い**。
  見逃しの記録は、通知試験（`monitoring/alert-tests.md`）と手動の障害注入でしか増えない。
- 誤検知の候補になりうるもの: runner の起動遅延（timeout 不足）、リリース直後の起動中（SUP-001 が抑制）、画面の文言・DOM 変更による locator のずれ（RB-004）。
